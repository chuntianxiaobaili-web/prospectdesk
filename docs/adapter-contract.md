# Mail/browser adapter contract

This document describes the original approved-packet `SalesWorkflow.mailAdapter` contract. `MockMailbox` and `BrowserMockMailbox` are test fixtures. The v0.3 existing-draft CUA adapter uses a separate contract and registered session tools: see [browser-mail-session.md](browser-mail-session.md). Do not inject that adapter into `SalesWorkflow.mailAdapter`; its hashes, preflight, receipt and cleanup signatures are different. A live adapter for this original route must implement every requirement below.

- `mode`: `mock` or an explicitly validated production adapter label.
- `checkCompatibility({accountId,signal})` returns a read-only compatibility result. The browser fixture requires a ready dedicated browser and checks the owned test page and unique mailbox controls. Use sanitized check results for subagent review. The check never fills, clicks, or submits a message. Missing or ambiguous controls require a hold and a fresh check before resuming.
- `preflight({recipient,accountId,threadId,signal})`: fresh checks immediately before dispatch, return `{accountId,accountVerified:true,recipientVerified:true,fresh:true}` only after checking account identity, correct recipient/company association, latest thread replies, stops, hard bounces and prior sends. Set `stop`, `hardBounce`, `latestReply`, `ambiguousRefusal` or `alreadySent` to hold. One mailbox is serially locked for both preflight and send.
- `send({idempotencyKey,recipient,company,subject,body,approvedHash,threadId,replyToMessageId,signal})` is called by the fixed executor with the exact approved packet. Preserve the recipient and content. Respect cancellation and settle once owned browser work stops. Recheck browser controls on the compose page before writing or clicking. No execution model is required.
- Return `{status:'sent',messageId,recipient,approvedHash,mode}` only with authoritative sent-folder/message evidence for exact recipient and approved content. This denotes sent confirmation, **not delivered**. Missing/contradictory receipt or any exception is unknown. A raw send-button click is not confirmation.
- `reconcile({idempotencyKey,recipient,approvedHash})`: authoritative matching sent evidence above; or `{status:'not_sent',authoritative:true}` only if absence is genuinely conclusive; otherwise `{status:'unknown'}`. Absence from a stale/unloaded list is not conclusive.
- No hidden re-tries inside adapter after uncertain browser action. Keep stable idempotency key across reconciliation. No attachments in v1 packets.
- Preserve authoritative evidence for any acceptance that predates a pause. Report uncertainty when acceptance cannot be resolved.

## Cleanup for an existing mailbox draft

A mailbox adapter that supports cleanup must use a stable, provider-backed draft selection and prove the association during fresh preflight. The preflight receives `idempotencyKey`, `subject`, `body` and `approvedHash` in addition to the existing account, recipient and thread fields. Return an optional `draftBinding: {accountId,draftId,draftVersion,approvedHash}` only after checking the exact existing draft, its current version, account, recipient and full content against the approved packet. An ambiguous or changed draft requires a preflight hold. A matching subject alone never identifies a draft. Messages composed without an existing draft retain their current send behavior.

The sender receives the captured binding with the approved packet. A bound send must recheck the exact version before dispatch. For cleanup, the authoritative send receipt must include `authoritative:true` and repeat the exact `draftBinding` from preflight. Reconciliation receives the account and optional original binding and must provide the same proof for any confirmed send.

After the program records the authoritative sent receipt to disk, it may call `trashSentDraft` with the approved packet, its binding, `sentMessageId` and an abort signal. The adapter must confirm the receipt and reread the exact draft in Drafts. Move only that unchanged draft into recoverable Trash, using the provider's conditional version check or equivalent safe operation. Verify Trash and draft state after the move. If the provider already removed the exact draft, record authoritative absence. Return `{status:'trashed'|'already_absent',authoritative:true,draftBinding,sentMessageId}` only with this evidence. Unsupported operations, changed or ambiguous drafts, and unknown outcomes require review. Permanent deletion and subject-based matches are outside this contract.

Draft cleanup has a separate recorded status. A crash or uncertain cleanup leaves a confirmed send intact. Once the fixed queue is idle, reconciliation of pending cleanup checks the same original binding and never sends the message again. The browser fixture composes new mock mail and has no preexisting draft cleanup operation. The in-memory fixture covers recovery, Trash and confirmed absence.
