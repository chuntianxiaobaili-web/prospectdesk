# 从产品资料到邮箱草稿的交接

## 本轮产品证据模式

用户选择以现有产品资料和逐封审核继续。配置 draftingPolicy.mode 为 product-evidence-review，品牌事实与实际读取的来源写入 brand.verifiedFacts 和 brand.evidenceSources。默认100来源学习模式仍供另一路线使用；本模式不生成虚假的已读来源或已批准手册。

正式稿记录产品依据快照和摘要。修改产品事实、来源或写稿模式后，原稿的批准停止生效。收件人、双语稿、版本、历史与退订检查继续保留。

## 新稿链路

1. 读取产品与品牌资料；分别记录事实、采购需求推断与未知项。
2. 载入全部可用历史，查询实际邮箱。历史覆盖未核对完整的客户保留 provisional，不自动升级。
3. 通过原 set_draft 保存完整双语稿，展示准确收件人、全文、版本及摘要，由用户逐封审核。模型没有 approve 工具。
4. 使用 sales_browser_mail_save_approved_draft({leadId, expectedCoreHash}) 保存当前已批准的英文原文。工具只读取该批准快照，不接受额外正文覆盖，也不发送。
5. 程序通过浏览器填写收件人、主题与英文全文，优先切换纯文本，替换默认签名后核对没有额外抄送；只执行草稿保存。保存后最多8次新鲜只读观察等待保存候选状态，不重复点击或新建。
6. 保存前后完成限定草稿搜索，确认唯一的新原草稿 ID，再打开读回完整收件人、主题和正文。保存提示或数字徽标不作为完成证明。
7. 核实后写入交接记录。coreApprovalHash 与 mailboxContentHash 分开保存，保留核心修订号、邮箱原草稿版本和账号。
8. 使用 sales_browser_mail_prepare_approved_drafts 以获批 leadIds 准备固定会话。新路线从持久化交接记录生成准确引用，不让调用者改写草稿 ID 或正文；旧现有草稿入口遇到已绑定新稿时引导到此路线。
9. start 才启动一次发送工作窗口，随后 step 串行执行。发送等待后再次核对当前批准、产品依据、账号与原文，变更即停止。
10. 已发送回执、原草稿清理和到点停止仍由原固定执行器处理。交接的保存尝试、已用状态和运行编号持久化，重启不自动重复创建或发送。

## 不确定结果

保存失败或结果不明时保留本次尝试记录，先核对实际邮箱，不自动重建、不删除草稿。可信宿主可用 reconcileApprovedDraftSave 对可见的准确原ID作只读恢复，仍需完整搜索和全文一致；恢复不调用save、send或delete。发送未知与清理未知分别保留，已确认发送不会因清理失败重新发送。只读回执核对不要求继续保持尚未过期的发送批准，但不会据此重新发件。

## 页面范围

当前新稿保存器针对已观察的中文CUA编辑页。纯文本直接读取完整值；富文本通过可见iframe正文按严格DIV/P/BR/A行结构还原全文，并保留读取方式与原AX摘要。未知结构或额外正文暂停。专用Chromium桥对多frame页面仍会暂停，因此不能把Edge CUA结果当作三个专用连接都已通过邮箱完整流程。

本轮已有两封获批原文在真实Edge邮箱完成保存及完整读回，实际发送和清理均为0。后续仍需分别验证发送、回执、确认后原草稿清理及截止；各浏览器结果以独立日志为准。
